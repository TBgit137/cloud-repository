The Parallelism Spectrum
From Cloud to Edge: Different Scales, Different Challenges
The Challenge:
Modern ML systems span an enormous computational spectrum - from 
data center training with thousands of GPUs to inference on 
microcontrollers with single-digit milliwatt power budgets. Each scale 
presents unique parallelism opportunities and constraints.
Scale Spectrum:
• Data Center: 8-1000s of GPUs, unlimited power, high-bandwidth 
interconnects
• Mobile/Edge: 4-8 cores, battery constraints, moderate memory
• Microcontroller: Single core, <1mW power, <1MB memory
Real-world Impact:
A transformer model training uses data parallelism across 256 GPUs, 
while the same model deployed on a microcontroller must use 
temporal parallelism within individual operations to meet power 
constraints.

Data Parallelism Fundamentals
Distributing Datasets for Parallel Training
Core Concept:
Data parallelism splits training datasets across multiple devices, with each device 
maintaining a complete copy of the model. This approach scales naturally with 
dataset size and provides linear speedup under ideal conditions.
Mathematical Foundation:
For N devices processing batch size B:
• Global gradient equals to the average of local gradients: 𝑔_𝑔𝑙𝑜𝑏𝑎𝑙 = (1/N) × 
Σ(g_i) where 𝑔_𝑖 is local gradient 
• Equivalent to single device with batch size 𝑁 × 𝐵
• Maintains SGD (Stochastic Gradient Descent) mathematical properties
Device Coordination:
1. Dataset splitting into non-overlapping subsets
2. Independent forward and backward passes
3. Gradient synchronization via ring all-reduce
4. Synchronized parameter updates
Scaling Benefits:
Linear speedup possible up to communication bottleneck threshold.

===== PAGE 6 =====
Quick 
Review – 
Stochastic 
Gradient 
Descent
The core idea of SGD is to update the model's parameters using the gradient 
calculated from a small, randomly selected subset of the training data, known as a 
mini-batch, rather than the entire dataset. In its purest form, SGD updates parameters 
using only a single data point at a time, though using mini-batches is more common in 
practice and often referred to as SGD.
• Mathematical Formulation: For model parameters θ, learning rate η, and loss L(θ):
• Standard Gradient Descent:θ𝑡+1 = θ𝑡 - η∇L(θ𝑡) (uses full dataset)
• Stochastic Gradient Descent: θ𝑡+1 = θ𝑡 - η∇Lᵢ(θ𝑡) (uses single random example i)
• Mini-batch SGD (most common): θ𝑡+1 = θ𝑡 - η∇LB(θ𝑡) - Where B is a mini-batch of 
examples and ∇LB(θ𝑡) = (1/|B|) Σi∈B ∇Lᵢ(θ𝑡)
Algorithm Steps 
1. Initialize model parameters θ0 randomly 
2. Shuffle the training dataset 
3. For each epoch (pass through the dataset):
         - For each mini-batch B in dataset: 
             - Compute gradient ∇LB(θ𝑡) 
             - Update parameters: θ𝑡+1 = θ𝑡 - η∇LB(θ𝑡) 
4. Repeat for multiple epochs until the loss becomes sufficiently small or stops 
improving
Example Update Rule: For linear regression with MSE loss: L(θ) = (1/2n)Σ(yᵢ - θᵀxᵢ)²
SGD update for parameter θⱼ: θⱼ ← θⱼ + η(yᵢ - θᵀxᵢ)xᵢⱼ

Data Parallelism Mechanics
Data Parallelism Fundamentals
Step-by-Step Execution Process
Execution Flow:
Input Data → Split into Batches → Distribute to GPUs
     ↓
GPU 1: Forward Pass → Backward Pass → Compute Gradients
GPU 2: Forward Pass → Backward Pass → Compute Gradients  
GPU 3: Forward Pass → Backward Pass → Compute Gradients
GPU 4: Forward Pass → Backward Pass → Compute Gradients
     ↓
Gradient Synchronization (Ring All-Reduce)
     ↓
Parameter Update on All Devices → Next Iteration
Communication Pattern:
Ring all-reduce algorithm minimizes communication 
overhead:
• Each device communicates only with neighbors
• 7 steps for 8 devices vs. 56 for naive peer-to-peer
• Bandwidth usage scales optimally with device count
Implementation Example:
Modern frameworks like PyTorch DistributedDataParallel 
handle synchronization automatically.

Data Parallelism Mechanics
Memory Constraints:
175B parameter model requires:
350GB for FP32 parameters
Additional memory for optimizer states and 
activations
Total: >1TB per device requirement
Exceeds current GPU memory (80GB high-end)
Workload Imbalance:
Heterogeneous systems suffer from device speed 
mismatches.
Scaling Limitations and Communication Overhead
Communication Bottleneck:
For 1B parameter model with 8 GPUs:
• Gradient data: ~4GB per synchronization step
• High-speed interconnects required (NVLink: 900 GB/s, 
InfiniBand: 400 Gb/s)
• Communication time grows with model size and device count
Scaling Efficiency:
• 8 GPUs: typically 87.5% efficiency (7x speedup)
• 64 GPUs: typically 70-78% efficiency (45-50x speedup)
• Diminishing returns due to synchronization overhead
NVLink is NVIDIA's high-speed, direct GPU-to-GPU interconnect technology 
designed for within-node (intra-node) communication to create unified 
memory pools and enhance multi-GPU workloads like AI and deep learning.
InfiniBand is an open-standard, high-bandwidth, low-latency networking technology for 
inter-node (between-node) communication, used to connect servers, storage, and other 
devices in large-scale clusters for distributed computing, HPC, and cloud environments.

Model Parallelism Strategies
Coordination Pattern:
Forward pass: sequential data flow through 
device chain
Backward pass: gradient propagation in 
reverse order
Parameter updates: local to each device 
partition
Mathematical Equivalence:
Distributed computation maintains identical 
results to single-device execution.
Tensor Parallelism
Splits individual layers (weight matrices, 
tensors) across GPUs. Every GPU processes a 
piece of the same layer at the same time.
Distributing Neural Networks Across Devices
When Model Parallelism is Necessary:
• Model parameters exceed single device memory
• Examples: GPT-3 (175B parameters), large vision transformers
• Memory requirement exceeds available hardware capacity
Partitioning Approaches:
1. Layer-wise: Sequential layer distribution across devices
2. Operator-level: Split operations within layers (attention 
heads, matrix dimensions)
3. Pipeline: Overlapped execution with microbatching

===== PAGE 24 =====
Pipeline Parallelism - Microbatching
This naive "layer-wise" parallelization is inefficient 
because it's sequential. Only one device works at a time 
while the others sit idle, leading to poor hardware 
utilization.
Splitting the input into microbatches allows devices to 
work simultaneously on different data chunks. This 
overlaps computation and drastically cuts idle time 
("bubbles"), reducing them from (m-1) to (m-1)/b 
(where m is stages, b is microbatches).
Basic Pipeline Problem:
Time →
Device 1: [Compute]      [Idle]            [Idle]           [Idle]
Device 2:     [Idle]       [Compute]       [Idle]           [Idle]  
Device 3:     [Idle]            [Idle]       [Compute]      [Idle]
Device 4:     [Idle]            [Idle]            [Idle]       [Compute]
Pipeline Solution with Microbatches:
Time →
Device 1: [F₀] [F₁] [F₂] [F₃] [B₃] [B₂] [B₁] [B₀]
Device 2:        [F₀] [F₁] [F₂] [B₂] [B₁] [B₀] 
Device 3:               [F₀] [F₁] [B₁] [B₀]
Device 4:                      [F₀] [B₀]
F = Forward pass, B = Backward pass, subscript = microbatch number

power linearly
• Must justify parallelism 
benefits vs. power cost

• Limited memory bandwidth 
restricts parallel data access 
patterns.

Duty Cycling Strategies
Trading Computation Time for Power
Basic Duty Cycling:
Power Reduction Calculation:
• Active: 10mW for 100ms every 1000ms
• Sleep: 0.1mW for 900ms every 1000ms
• Average: (10×0.1 + 0.1×0.9) = 1.09mW
• vs. continuous 10mW operation
Frequency Scaling:
Lower clock frequency reduces power 
quadratically:
• 48MHz: 2mW
• 24MHz: 1.2mW
• 8MHz: 0.4mW
Trade computation speed for power savings
