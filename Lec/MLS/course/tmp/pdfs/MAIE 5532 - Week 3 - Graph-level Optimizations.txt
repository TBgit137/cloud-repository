Shapes

Both Matrices A and B are partitioned into fixed-size tiles that match

Data Layout Transformations
NHWC
• Order: Batch, Height, Width, Channels
• What it means: For each pixel, all its 
color/feature values are stored next to 
each other.
• Typical: TPUs/mobile NPUs; kernels that 
combine channels at a pixel
• Order in the above image: pixel 1(red)-> 
pixel 1 (green), pixel 1 (blue), pixel 
2(red), pixel
NCHW
• Order: Batch, Channels, Height, Width
• What it means: For each channel, all the 
pixels in the image are stored next to each 
other.
• Good when: You sweep over images one 
channel at a time.
• Typical: Convolution on many GPUs
Reorder/transpose axes
Example permutation: [0, 3, 1, 2] 
turns NHWC into NCHW
No data changes—just the order 
we store it.
Pixel 1 Pixel 2 Pixel 3 Channel R Channel G Channel B
• N: Number of images in the batch.
• C: Number of Channels per image (e.g., 3 for Red, Green, Blue).
• H: Height of the image in pixels.
• W: Width of the image in pixels.
For large matrix multiplies, we often go beyond NHWC/NCHW 
and use packed tile layouts that match the GEMM kernel 
GEMM stands for General Matrix Multiplication. It's the 
mathematical name for the core operation that powers 
deep learning and scientific computing: multiplying two 
large matrices together. 

===== PAGE 26 =====
Cache-
aware 
Scheduling
Why it matters: 
• Minimizes cache misses by keeping hot data in faster caches 
(L1/L2) longer.
How it works: 
• Reorder and group operations to reuse data while it’s still in 
cache.
• Tile/block loops so working sets fit in L1/L2; promote shared 
data to L3-friendly batches.
• Align access patterns for spatial and temporal locality.
Practical tactics: 
• Loop tiling/blocking, fusion, and interchange to reduce working-
set size.
• Prefetching and software-managed buffers when available.
Cache is a small, fast memory layer that sits 
between the CPU and main memory to reduce data 
access latency. It stores recently used (and nearby) 
data so the processor can reuse it quickly. L1 cache 
is the smallest and fastest, located closest to the 
CPU cores and split into instruction/data caches. L2 
is larger but a bit slower, often private per core. L3 
is much larger and slower than L1/L2, typically 
shared across cores on a chip, helping reduce trips 
to main memory by serving common data.

LSTMs (Long Short-Term Memory networks) are a type of recurrent neural network (RNN) 
designed to handle long-term dependencies in sequential data. Unlike basic RNNs, which 
struggle to remember information over long sequences, LSTMs use special "gates" (forget, 
input, and output gates) to control what information is stored, updated, or discarded in their 
internal memory. This allows them to retain important context, while ignoring irrelevant 
details. LSTMs are useful for tasks like language translation, chatbots, and predicting 
sequences where past information is crucial for accurate results.
GRUs (Gated Recurrent Units) are a simpler and more efficient version of LSTMs, designed to handle 
sequential data like text or time series. Unlike LSTMs, which have three gates (input, forget, output), 
GRUs use just two gates—an update gate (decides what past information to keep) and a reset gate 
(determines what to forget). They combine short-term and long-term memory into a single hidden 
state, making them faster to train while still capturing important patterns. GRUs are great for tasks 
like autocomplete, translation, or chatbots, where context matters but computational efficiency is 
key. They’re newer (2014) and often perform as well as LSTMs with less complexity.

# Simple model component
class Block(tf.Module):
  def __init__(self, c): super().__init__(); self.conv = 
tf.keras.layers.Conv2D(c, 3, padding="same")
  def __call__(self, x, training=False):
    x = self.conv(x)

training=training)

3. Multi-Level Intermediate Representation (MLIR):
MLIR is not a compiler itself but a framework for building compilers. It enables multi-stage optimizations across different 
abstraction levels.
Key Features:
• Flexible IR: Can represent high-level (e.g., TensorFlow ops) and low-level (e.g., LLVM IR) code.
• Domain-Specific Optimizations: Supports dialects (e.g., linalg for linear algebra, gpu for GPU ops).
• Reusable Passes: Compiler transformations can be shared across frameworks.
How It Works:
A model is progressively lowered from high-level ops to hardware-specific instructions.
Example flow:
TensorFlow Graph → MLIR (tf dialect) → MLIR (linalg dialect) → LLVM IR → Machine Code
• tf dialect = TensorFlow-specific ops.
• linalg dialect = Generalized linear algebra ops for compiler-friendly optimizations.
Use Case:
Used internally in TensorFlow, PyTorch, and TVM for flexible compiler pipelines.

Hardware-Specific Optimizations - 
Microcontrollers
Microcontroller Optimizations
Objective: Minimize memory and compute usage for resource-constrained 
devices (e.g., ARM Cortex-M).
Key Considerations:
• Limited RAM/Flash memory (e.g., KBs of memory).
• No OS or dynamic memory allocators; avoid heap usage.
• Cache misses are costly; optimize access patterns.
Small Data Types:
• Use 8-bit integers (int8) or binary weights instead of FP32 to save memory.
• Quantization is critical (e.g., TensorFlow Lite for Microcontrollers).
Cache-Friendly Access:
• Use linear or sequential memory access to avoid cache thrashing.
• Avoid random jumps (e.g., linked lists).
Static Memory Allocation:
• Pre-allocate buffers during compilation (nomalloc at runtime).
Example:
• Replace a float32 dense layer with a int8 quantized layer, reducing memory 
by 4×.

Quantization for Latency
Core idea
• Reduce numerical precision of weights and activations to shrink models and speed up 
inference, especially on low-precision hardware.
Two approaches
• Post-training weight quantization (weights only)
• Convert FP32 weights to INT8/FP16.
• ~75% size reduction moving FP32 → INT8 (4:1).
• Faster loads, lower bandwidth, better cache fit.
• Limitation: activations stay FP32, so speedups are partial.
• Post-training integer quantization (weights + activations)
• Convert both to integers; uses integer compute units.
• Requires a representative dataset to calibrate activation ranges.
• Big gains on integer-optimized hardware; must validate accuracy carefully.
Hardware angle
• Microcontrollers: INT8 MACs are far faster; often no FP unit → integer quantization is 
essential.
• Mobile NPUs/DSPs: designed for low-precision arithmetic (e.g., Hexagon, Neural 
Engine).
• Universal wins: lower memory bandwidth, better cache locality, reduced power.

2. SIMD Instruction Utilization:
Key Idea:
• Single Instruction Multiple Data (SIMD) allows processing multiple data 
points in parallel, drastically improving throughput.
• Example: ARM NEON/Helium for Convolution
NEON (ARM Cortex-A) and Helium (ARM Cortex-M55/M85) are SIMD extensions.
How it works
• Instead of processing one multiply-accumulate (MAC) at a time, SIMD

• Example: A 128-bit NEON register can hold four 32-bit floats or sixteen 8-bit

models.

ML inference).
• Low-precision arithmetic (int8, int16) benefits

3. Memory Access Optimization (Cache-Friendly Patterns)
Key Idea:
• Modern CPUs have cache hierarchies (L1, L2, L3). Optimizing memory access patterns 
reduces cache misses and improves performance.
Problem:
• Naive matrix multiplication has poor locality (strided memory access → cache 
thrashing).
• Example: For large matrices, accessing b[j] may evict useful cache lines.
Solution: Tiling (Blocking)
• Break computation into smaller tiles that fit in L1/L2 cache.
• Each tile is reused multiple times before eviction
Why Tiling?
• Reduces DRAM bandwidth pressure.
• Can provide 2–3x speedup for large matrices.
When to Use Tiling:
• Large matrix multiplications (common in deep learning).
• Any memory-bound operation (e.g., image processing, 
FFTs).
// Optimize for cache-friendly access patterns
void tiled_matrix_multiply(const float* a, const float* b, float* c) {
// Process in cache-sized tiles
   const int TILE_SIZE = 32;  // Fits in L1 cache
   for (int i = 0; i < n; i += TILE_SIZE) {
   for (int j = 0; j < m; j += TILE_SIZE) {
      multiply_tile(&a[i*k], &b[j], &c[i*m + j]);
   }
   }
}

Benchmarking and Validation - 
Comprehensive Benchmarking
•Measure all three: accuracy, latency (cold and warm), and peak memory. 
•Optimizations are trade-offs; define acceptable accuracy loss for your app. 
Accuracy validation 
•Prevent functional regressions; a 10× speedup isn’t useful if accuracy drops 50%. 
•A 2× speedup with ~1% loss may be a win—depends on tolerance and domain. 
Latency measurement 
•Capture cold-start vs warm throughput; control for cache/heating/jitter. 
•Use medians with percentiles (p50/p95/p99) over multiple runs.
